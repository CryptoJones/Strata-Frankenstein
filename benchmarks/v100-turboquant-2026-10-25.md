# TurboQuant KV cache and Volta TQ prompt attention, 2026-10-25

## Scope

TurboQuant is an opt-in KV cache format for CUDA builds. Use `--kv tq3`, `tq4`, `tq6` or `tq8`.
Each 256-value head is rotated with a Hadamard transform.
The rotated values are quantized against a Lloyd-Max codebook.
Each head carries one FP16 norm.
The fit is minimum squared error only. This cut has no QJL residual.

The format is resident only. The K/V stays in VRAM, there is no host copy, and the engine refuses `--kv-resident`.
The MTP draft layer keeps its plain INT8 cache. The main layers use the selected width.
Setup does not offer these values. Nothing is a default, and the daily service stays on int8.

`STRATA_PROMPT_ATTN_TQ=1` enables a second opt-in: a tensor-core prompt reader for the four widths on sm_70.
Unset or `0` keeps the decode-attention fallback. The reader changes no KV bytes and no KV allocation.

This report has three measurements:

1. A cold 2,048-token-budget prefill and decode comparison of int8 and tq6.
2. A needle-in-a-haystack retrieval comparison of int8 and tq6.
3. Prompt-reader wall-time comparisons for tq6 and tq8, with int8 controls.

All runs use the regular IQ3_S assets and the native Qwen3.8-Flash-Next model.

## KV memory at full capacity

The table is calculated from the format sizes. The model has 12 attention layers, 2 KV heads and head dimension 256.
One cell holds K and V for one token in one layer.

| `--kv` | Bytes per cell | 524,288-token KV, 12 layers | Change from int8 |
| --- | ---: | ---: | ---: |
| int8 | 1,056 | 6.1875 GiB | — |
| tq8 | 1,032 | 6.046875 GiB | −0.140625 GiB |
| tq6 | 776 | 4.546875 GiB | −1.640625 GiB |
| tq4 | 520 | 3.046875 GiB | −3.140625 GiB |
| tq3 | 392 | 2.296875 GiB | −3.890625 GiB |

The tq6 main saving is 1.64 GiB at the full 524,288-token capacity.
These are capacities, not measured `nvidia-smi` reductions.
The expert cache fills the freed VRAM. Total GPU memory stays near 15,600 MiB in every arm below.
A smaller KV cache becomes more expert slots only with the elastic K/V.

The context capacity and the CPU memory defaults do not change. Only the bytes per KV cell change.

## Optimized prompt reader

The reader decodes selected compressed tiles into shared memory for the prompt path.
It does not keep a persistent FP16 cache. It applies the per-head norm once in FP32.
KV allocation and stored bytes do not change.
The reader is off by default and only runs on sm_70.

The harness starts a fresh service per arm with `STRATA_PREFILL_TIMING=1`.
It sends one authenticated request with `max_tokens=1` at 2,071 prompt tokens and one at 51,746 prompt tokens.
Wall time is the request wall time, not decode throughput.

## Validation and limits

- The CUDA full build passes.
- `conversation_snapshot_test` passes 6,709 checks, and `kv_tq_parity` passes.
  Both finish under CUDA Compute Sanitizer with zero memory errors.
  The state checks use the real allocation path: `qsa_state_bytes` and `qsa_state_init` carve the K/V
  arrays for tq3, tq4, tq6 and tq8, every extent stays inside the arena that init reports, and each
  array covers exactly its rows times `kv_tq_bytes_per_head`.
  They also cover a snapshot A/B/A round trip, a restore from another width rejected on payload size,
  and the mixed INT8 draft layer.
  The state fingerprint now reads the resident TQ arrays with the correct per-head byte stride.
  Snapshot width rejection uses payload size because the format tag does not encode the bit width.
- The three conversation tests and `kv_tq_parity` pass again after the shared VMM fix.
- The portable half-bit-cast GEMM test (`prefill_gemm_parity`) reports zero errors at 19x23x37.
- The full HIP build passes with hipcc 7.2.4 for gfx1100. This is a compile and link check only.
  There is no AMD card here; `kv_tq_parity` skips correctly, and no HIP TQ GPU run was measured.
  The host-side conversation validation passes in the HIP build.
- `kv_tq_parity` exits with code 77 when no device is present. Both the CUDA and the HIP build record
  that as a skip, not a failure.
- Eighteen CUDA target regression tests ran while the live int8 service held both cards.
  Twelve passed. Six stopped on out-of-memory errors: `qsa_slots_parity`, `qsa_slots_parity_lanecell`,
  `qsa_merge_daily_parity_default`, `qsa_merge_daily_parity_daily`, `kv_stream_parity` and
  `kv_window_parity`.
  These runs failed at allocation while the service occupied the cards; they cannot establish a regression verdict.
  They were not rerun on idle cards, and they are not claimed as passes.
- The CPU-only full build and CTest pass: 55 tests pass and 4 skip, 59 in total.
- These checks add no speed or quality claim. The measurements above stay tied to the executable
  SHA-256 and the HEAD recorded in "Build and settings"; the checks in this section ran on the current
  integration tree.
- The SYCL compiler is not installed here. SYCL has no TurboQuant implementation, its separate port is
  unchanged, and its command line rejects these values.
- Only tq6 and tq8 have prompt-reader measurements. tq3 and tq4 have no reader measurement.
- Only tq6 has needle results. tq3, tq4 and tq8 have no needle or perplexity results.
- The prefill comparison has one run per size per arm, and the first generated token differs between the arms.
- The settings check reports two harness mismatches (`--spec`, `--vram-reserve-mib`).
- These runs do not show a speed gain. The tq6 prompt path is slower than int8.
- The daily service is unchanged and stays on int8.
- The CPU capacity defaults are unchanged.

### HIP build fixes

The HIP build needed four corrections before it could configure, compile and link:

- **Runtime target in CMake.** `prefill_gemm_parity` is built for every GPU backend, but it linked
  `CUDA::cudart` and used the CUDA-only include variable, so a HIP configure failed with CMP0028 before
  any object was built. The target now uses the backend-neutral runtime include and link variables.
  The gfx906 HIP build turns on the CUDA-shaped branch but enables only the HIP language, so it also
  leaves out a target whose source is forced to CUDA.
- **Portable half bit cast.** Under HIP the parity test's host file is compiled by the system compiler,
  and those half headers have no `__half_as_ushort` or `__ushort_as_half`. `std::bit_cast<uint16_t>`
  reads the same bits on both toolchains.
- **Stale test scorer launch.** The test-only reference arm still launched the old warp grid: one block
  per `SCORE_WARPS` key rows and one per query. The production dispatcher scores `QUERY_TILE` queries
  per block against `KEY_GROUPS * SCORE_WARPS` key rows, so the test now uses that grid and stays in
  step with the kernel's contract.
- **Per-device VMM ABI.** The HIP VMM helper kept one process-wide device id and allocation
  granularity. Each range now records the device it was created on and that device's granularity, so
  every map, unmap and access call uses the values captured with the range. HIP uses
  `hipMemAddressReserve`, `hipMemCreate`, `hipMemMap` and `hipMemSetAccess`; `STRATA_HIP_VMM=0`
  turns it off.
