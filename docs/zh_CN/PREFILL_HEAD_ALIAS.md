# 把输出头的显存借给 prompt 通路（`--prefill-head-alias`，需手动开启）
<a id="lend-the-output-heads-vram-to-the-prompt-path---prefill-head-alias-opt-in"></a>

两个显存大户从不同时工作。原生输出头（output head，IQ3_XXS 的 Q5_K 头为 417 MiB）把最后的隐状态变成 logits，
所以只在生成 token 时才需要。批量 prompt 通路的缓冲区只在读 prompt 时才需要。加上
`--prefill-head-alias` 后，引擎改为轮流使用：读 prompt 时，输出头的显存用来放 prompt 缓冲区；第一个生成的
token 之前，再把输出头读回来。

该开关默认关闭。关闭时，引擎的行为与以前完全一样。

## 为什么要这样做
<a id="why"></a>

在 8 GB 的卡上，prompt 分块（chunk）的大小受空闲显存限制，而 prefill（预填充）速度与分块大小紧密相关。
下面是同一个 29,854 token 的 prompt，每次试验都起一个全新的引擎，每次只发一个请求。卡与设置列在
[实测](#measurements)一节。

| prompt 分块 | 试验次数 | prefill 中位数（范围） | 引擎是怎么做到的 | 启动后的空闲显存 |
|---:|---:|---:|---|---:|
| 256 | 4 | 185.5（177.8-195.9）tok/s | `--prefill auto`，预留 686-745 MiB | 383-443 MiB |
| 512 | 12 | 292.5（281.0-306.1）tok/s | `--prefill auto`，预留 442-667 MiB（590 是我们调好的取值） | 137-365 MiB |
| 768 | 7 | 387.4（375.8-397.2）tok/s | `--prefill auto`，预留 331-405 MiB | 27-103 MiB |
| 1,024 | 4 | 442.9（440.8-444.1）tok/s | `--prefill auto`，预留 239-295 MiB | 0 MiB |
| 1,280 | 5 | 514.5（512.8-517.3）tok/s | `--prefill auto`，预留 147-221 MiB | 0 MiB |
| 1,536 | 2 | 573.6（571.0-576.3）tok/s | `--prefill auto`，预留 73-110 MiB | 0 MiB |
| 1,792 | 3 | 631.4（628.7-632.9）tok/s | `--prefill auto`，预留 0-36 MiB | 0 MiB |
| **2,048** | **6** | **667.1（661.5-667.7）tok/s** | **`--prefill-head-alias`，预留 590 MiB** | **289 MiB** |

不加开关时，768 token 以上的每个分块都只能靠调低 `--vram-reserve-mib` 换来，而那样只剩下 0 MiB 空闲。
在 WDDM 下，这正是 Windows 开始分页（paging）的状态。加上开关后，2,048 token 的分块是在 590 MiB
预留不变的情况下得到的。

## 它做了什么
<a id="what-it-does"></a>

1. **启动时**，MTP 草稿层从输出头复制完自己的草稿头行之后，输出头就被卸载。
   自动专家缓存随后按“输出头的显存算作空闲”来定大小（在我们的卡上：749 个槽位而不是 508 个）。
   prompt 通路借用缓存槽位 1 到 N（槽位 0 保留）。放不进这些槽位的部分由 prompt 通路自己分配，
   于是形成“hybrid”布局。分块取 2,048、1,536、1,024 和 512 token 中最大的那个，
   条件是其缓冲区能放进借来的槽位加上空闲显存、并留出 512 MiB 余量。
2. **对每个请求**：
   1. 如果输出头已加载，就卸载它，并重新布局 prompt 通路（中位数 20 ms）。
   2. 读取 prompt。
   3. 把借出的槽位填回去，释放 prompt 通路自己的缓冲区。
   4. 在第一个 decode（解码）窗口之前重新加载输出头（中位数 255 ms）。
3. **图的安全性。** 各 verify 窗口的 CUDA graph 在第一次 decode 时捕获，其中保存着输出头的地址。
   如果之后某次重新加载把输出头放到别的地址，引擎会带着错误停止，由服务器重新启动它。
   它不会去跑指向已释放内存的图。我们从未见过这种情况发生；见
   [待解问题](#open-questions)。

在以下情况下，引擎会拒绝该开关并给出原因：没有 `--serve`、多于一块 GPU 或有层切分、带
`--batch`、带 `--pipeline-windows`、`--short-read` 大于 0、固定的 `--expert-cache` 大于 1、没有 `--mtp`，
或没有原生输出头。

## 代价
<a id="costs"></a>

- **短读变慢。** 每个请求都要重新加载输出头（2,717 次恢复的中位数为 255 ms，p90 为 261 ms，最大
  495 ms）并重建 prompt 通路（20 ms）。它还要借出几乎整个缓存、之后再填回，即使只读少量
  token 也是如此。把以上全部算在内的引擎自身 prompt 时间，按读到的新 token 数（生产环境，中位数）：

  | 读到的新 token | 默认 | 输出头别名 |
  |---:|---:|---:|
  | 1-64 | 671 ms（293 个请求） | 1,311 ms（614） |
  | 65-512 | 1,703 ms（409） | 2,453 ms（955） |
  | 513-2,048 | 4,062 ms（278） | 3,331 ms（618） |
  | 2,049-8,192 | 15,206 ms（118） | 6,876 ms（277） |

  所以该开关在 512 token 以内的读上大约多花 0.6-0.75 s，而从 513 到 2,048 token 之间的某个点开始划算。
  在 agent 循环中，2,717 个请求里有 614 个读到的新 token 不超过 64 个。
- **解码时空闲显存更少。** 默认那次运行中，verify 窗口捕获时有 207-287 MiB 空闲。加上
  开关后，捕获时只有 0 MiB 空闲。在 2,717 个请求（约 26 小时）中，我们没有看到分页症状：decode
  从第一个请求到最后一个都保持在约 29 tok/s（见下表）。这是在其他卡和驱动上的主要风险。
- **每个 prompt 之后要填回的槽位更多。** prompt 通路借走几乎整个缓存（749 个槽位中的 748 个，而不是
  508 个中的 328 个），所以每个 prompt 之后要复制回来的专家层更多。这部分时间已计入上面的 prompt 时间。

## 实测
<a id="measurements"></a>

本页所有数字所用的卡与设置：

- NVIDIA RTX PRO 2000 Blackwell Laptop GPU，8,151 MiB，Windows 11 Pro（WDDM，驱动 597.16），CUDA 13.0，sm_120。
- Intel Core Ultra 9 285H（AVX2），64 GiB 内存，PCIe 探测 25 GB/s（自动选出的 `pcie_frac` 0.55）。
- Qwen3.8-Flash-Next IQ3_XXS 原生模型包，`--max-context 262144`、`--kv q4_0`、`--kv-resident 32768`、`--spec 4`、
  `--spec-min-p 0.5`，MTP 使用英文草稿词表，`--prompt-cache 3`、`--vram-reserve-mib 590`、
  `--expert-cache auto`、`--prefill auto`。
- 引擎是带本次改动的本地 0.1.41 构建。两边还都用了本地的一个 `STRATA_ARENA_REGISTER=0` 开关，
  它不属于本次改动：它跳过本机上对 40 GiB arena 的 `cudaHostRegister`。

### 受控：一个 prompt，一个强制输出
<a id="controlled-one-prompt-one-forced-output"></a>

每次试验都在 29,854 token 的 prompt 上起一个全新的引擎。同一个 3,072 token 的续写被强制成每个
token 一行 verify，不用投机（spec）草稿，因此各次 decode 数字比较的是同样的工作量。强制由一个本地基准开关完成；
它不属于本次改动。

| 设置 | 试验次数 | 专家槽位 | prompt 分块 | prefill | decode | 专家缓存命中 |
|---|---:|---:|---:|---:|---:|---:|
| 1 槽位缓存 | 4 | 1 | 1,024（自有缓冲区） | 441.0 tok/s | 22.26 tok/s | 0.2% |
| 1 槽位缓存 + 输出头别名 | 2 | 1 | 2,048 | 666.3 tok/s | 24.50 tok/s | 0.2% |
| 自动缓存 + 输出头别名 | 3 | 749 | 2,048 | 667.7 tok/s | 26.21 tok/s | 24.9% |

我们没有在这种强制模式下跑默认配置（自动缓存、无输出头别名）。它在同一个 prompt 上的自由运行结果
是第一张表的 512 token 那一行：在 590 MiB 预留下的一次试验读到 306.1 tok/s、decode 为 27.9 tok/s，
而六次输出头别名试验的 decode 为 26.6-29.0 tok/s（中位数 27.9）。自由运行的输出逐次试验各不相同，
所以它们的 decode 速率只是粗略比较。

### 生产环境：agent 循环
<a id="production-an-agent-loop"></a>

工作负载是 OpenCode 的 agent（worker、reviewer 和 retrospective），它们针对 `/v1/chat/completions`
跑编码循环。prompt 最长约 150K token，并用 `--prompt-cache 3` 做前缀复用。

- 默认：8 个循环轮次内 1,200 个请求。
- `--prefill-head-alias`：20 个轮次内 2,649 个请求。

该开关还要求 `--short-read 0`；默认那次用的是 64。其余设置都相同。速率取自引擎自己的日志行
（`reading the prompt` 进度至少持续 5 s，以及输出至少 32 token 的请求的 decode 速率）。比较是在
16K token 的上下文区间内进行的，因此两边的 prompt 组合轻重不同不会被算作速度变化。区间是 95% bootstrap 区间。

| | 默认 | 输出头别名 | 上下文区间内的变化 |
|---|---:|---:|---:|
| prefill 中位数 | 256 tok/s | 583 tok/s | +125%（+123% 到 +129%） |
| decode 中位数 | 24.8 tok/s | 29.2 tok/s | +19%（+17% 到 +23%） |
| 专家缓存命中率中位数 | 20.8% | 25.9% | 508 -> 749 个槽位 |

decode 的差异需要谨慎看待。默认的各次运行在接近 27.5 tok/s 的长段和接近 19.5 tok/s 的长段之间交替。
51 个请求的滚动中位数显示出一段段各含数百个请求的平台，而且有一次运行里从慢到快的切换并没有伴随着
引擎重启。在输出头别名那次运行中，2,649 个请求的每十二分之一的中位 decode 为 28.7-29.8 tok/s。
只与默认运行的快段相比，decode 约快 6%。我们不知道慢段是什么造成的，因此并不声称本次改动消除了它们。

两次运行之间还重新编译了引擎二进制，以便把 prompt 缓存支持加进本次改动。上面的受控表才是
固定同一个二进制所做的比较。

## 在 0.1.43.1 上的移植检查
<a id="port-check-on-01431"></a>

本次改动被移到上游 main（0.1.43.1），并在同一台 PC 上做了检查。两次运行都用同一个构建、每次都起新引擎，
并使用 `STRATA_ARENA_PIN_GIB=auto`：没有它，这台 64 GB 的 PC 上对完整分片 arena 的页锁定会让 WDDM
只剩 0 GiB 给缓存（#243）。请求是冷启动的 29,842 token prompt、在其前缀上的一次 31 token 追问、
两个 45 token 的 prompt，然后又是那个长 prompt。输出上限设为 768 token 并启用低推理，生成是自由运行（未强制）。

| | 默认 | 输出头别名 |
|---|---:|---:|
| 专家槽位、prompt 分块 | 507、512 | 753、2,048 |
| verify 窗口捕获时的空闲显存 | 207-245 MiB | 0 MiB |
| 冷启动 29,842 token prompt，两次运行 | 276.5、277.1 tok/s | 643.1、649.7 tok/s |
| 那两次的 decode | 35.7、34.7 tok/s | 34.1、31.6 tok/s |
| 31 token 追问（复用 29,837），prompt 时间 | 632 ms | 1,721 ms |
| 45-46 token 的 prompt，prompt 时间 | 871、1,005 ms | 1,780、1,424 ms |

五个请求全部完成，回答连贯。输出头每次都回到同一个地址，所以保护检查从未触发。0.1.43.1 新增的
请求开始告警（“below 1024 MiB free”）在两种设置下都会出现：默认时是 289 MiB，加上开关时是 0 MiB。

## 待解问题
<a id="open-questions"></a>

- **给输出头一个固定地址。** 输出头是用 `cudaMalloc` 放回去的，它不保证是同一个地址。上面的
  检查把“地址变了的输出头”变成一次干净的引擎重启。更干净的做法是保留输出头的虚拟地址区间、只换掉其
  后端存储（CUDA VMM），或者把 prompt 缓冲区直接铺进输出头的分配里，而不是先把它释放。
- **短读时跳过这次换入换出。** 只读几十个新 token 的请求，要为一个它用不上的 2,048 token 分块付出约
  0.6 s（见上表）。对读到的新 token 数设一个阈值，低于它就保留输出头、让这次读像 `--short-read` 那样
  走 decode 窗口，就能省掉这部分代价。
- **其它卡。** 我们只在 Windows 上测了上面那张 8 GB 卡。更大的卡不加开关也能拿到大的分块，
  所以我们预计那里的收益会更小。
