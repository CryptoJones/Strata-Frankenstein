# 一份长文档，许多问题（0.1.40.2，可选开启）
<a id="one-long-document-many-questions-01402-opt-in"></a>

把一份长文档读一次，然后问许多不同的问题而不用重读。所有数字：Tesla P100 16 GB，
IQ2_XS，`--kv int8 --kv-resident 32768`，开启 MTP，greedy，除某行注明 “pin” 外均为 0.1.40 引擎。

## 引擎已经做到的（0.1.40）
<a id="what-the-engine-already-did-0140"></a>

会话缓存会保存小的检查点（GDN 和 indexer 状态，各约 118 MiB）；文档的 K/V
留在会话里，因此从某个检查点开始的问题只需读取该检查点之后的部分。

| 262K 文档（258,655 个 token） | 首 token 时间 |
|---|---|
| 第一个问题（冷读） | 904 s（286 tok/s） |
| 第 2-20 个问题，引擎在文档末尾设了回合边界 | 中位数 0.53 s（0.44-0.72） |
| 同样的问题走服务器的 chat API（文档末尾没有回合边界） | 每个 55.5 s（测了 15 个）：引擎会从最近的周期检查点重读最多 `--prompt-cache-every`（16,384）个 token |
| 服务器 `parallel` 2 | 前两个问题 918 s 和 979 s；接下来两个又从 token 0 重读文档 |

检查点内存：首次读取后常驻增加 +804 MiB（6 个检查点）；之后每个问题最多再增加 10 MiB。262K 的
K/V 占用 3.06 GiB 页锁定内存，每个会话一份（`--batch` 的每个槽位各自一份）。
输出一致性（greedy，64 个 token）：在全新引擎上问第 1 和第 12 个问题，得到的 token 与 20 问那一轮相同。
注意：IQ 模型在温度 0 下两次运行之间并非字节可复现，除非设置 `STRATA_IQ_MT_MIN=1`（DETAILS.md）；
原因就在于此，同一提示词两次运行的有些答案会不同，无论有没有下面这个字段。

## `strata_prefix`（以及引擎的 `pin=N`）
<a id="strata_prefix-and-the-engines-pinn"></a>

`"strata_prefix": {"messages": 1}`、`{"message": 0, "chars": N}` 或 `{"tokens": N}` 把提示词的开头标记为
共享文档。它末尾的检查点会被钉住：永不被回收，留在停放会话（parked-conversation）的预算里，被
`SAVE` 保留，而从它恢复的问题也不会把它离开的分支停放起来。

| 64K 文档（P100） | 无此字段 | 有此字段 |
|---|---|---|
| 引擎，原始提示词，第 2-5 个问题 | 48.6 s | 0.35-0.53 s |
| 两个问题之间插入一个 100K token 的分支，然后再问 | 149 s | 0.55 s |
| 中间再插入另一个 20K 提示词（`--conversation-cache-mib 8192`） | 49 s | 0.97 s（恢复后），然后 0.44 s |
| 服务器，18K token 文档，消息拆分 / 单条消息 | 8.8 s | 0.6-0.8 s |
| 服务器 `parallel` 2，六个问题 | 730 s（每一对都重读） | 220 s（第 3-6 个问题：2.5-3.8 s） |

跨 `--batch` 槽位的写时复制 K/V 页**没有**实现：每个槽位保留自己的 K/V（262K 时 3.06 GiB，1M 时约 12 GiB），
接纳一个分支会复制前缀 K/V（262K 时 3 s）。被钉住的前缀省掉的是重读，不是复制。

`tools/research_run.py` 会针对服务器跑一份文档和一组问题，分别带该字段和不带该字段。

## R3：专家槽位与 K/V block 的取舍（P100，IQ2_XS）
<a id="r3-expert-slots-against-kv-blocks-p100-iq2_xs"></a>

64K 文档，5 个问题。先 prefill，然后是一个短问题的首 token 中位数，然后是 decode：

| 专家槽位（GiB） | prefill | 首 token | decode |
|---|---|---|---|
| 2,083 (2.81) | 230 s | 0.69 s | 27.5 tok/s |
| 3,500 | 200.7 s | 0.61 s | 30.9 |
| 5,000 | 200.7 s | 0.55 s | 34.2 |
| 7,000 | 200.7 s | 0.51 s | 36.7 |

显存的边际价值：在 2,000 到 5,000 个槽位之间，每 GiB 每 200 token 的回答带来 0.31-0.41 s 的 decode，
再往上为 0.15；prefill 只在低于提示词借用（prompt loan）的下限时才有收益。显存里的 K/V cell
（`--kv-resident`）：4096 / 16384 / 32768 / 65536 在 64K 时给出
34.05 / 34.06 / 34.21 / 34.92 tok/s；在 262K（5,000 个槽位）时 8192 / 32768 / 131072 给出 29.54 / 29.46 / 29.49 tok/s
（block 命中率 92.6 / 94.5 / 95.7 %）。所以 K/V block 缓存每 GiB 不值什么，专家层只帮 decode，而
读取已经由借用承担。切分规划器能带来的收益几乎为零，所以没有实现。读取里唯一真正有效的杠杆是
chunk：`--prefill 16384` 配 7,000 个槽位，读 64K 用 186.4 s，而对照是 200.7 s（-7%），4096 则要 228 s；
它需要更大的借用额，并且改变分块方式、也就改变了舍入，所以这不是只改放置的改动。
