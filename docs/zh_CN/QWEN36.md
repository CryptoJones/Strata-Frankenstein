# Qwen3.6-35B-A3B：图片、同时多个请求与速度
<a id="qwen36-35b-a3b-pictures-several-requests-at-once-and-speed"></a>

Strata 在自己的引擎通路上运行 [Qwen3.6-35B-A3B](https://huggingface.co/Qwen/Qwen3.6-35B-A3B)（35B 专家混合，3B 激活，
256 个专家层，top-8），文件用 [Unsloth 带 MTP 层的 GGUF](https://huggingface.co/unsloth/Qwen3.6-35B-A3B-MTP-GGUF)
（UD-Q4_K_XL、UD-Q6_K_XL、Q8_0）；这条通路是 `src/qwen35`，`strata` 会按文件的架构切换到它。可以在应用的模型列表里选它，
也可以用 `strata launch` 或 setup（`--family qwen36`）选。除了文本，它还能读**图片**、并同时服务**多个请求**，
与 Flash-Next 模型具备的同样这两个选项。

实测在 AMD Radeon AI PRO R9700 32 GB（HIP，Linux，UD-Q4_K_XL，所有专家层都在显存里）和 RTX 3060 12 GB（CUDA，20 线程，
UD-Q4_K_XL 用 hybrid 模式：每层 256 个专家层里有 22-37 个在显存里，其余在 CPU）上进行，llama.cpp 972b5fc 跑同一批文件。

## 图片
<a id="pictures"></a>

视觉编码器是 Unsloth 的 `mmproj-F16.gguf`（0.9 GB，固定修订版，setup 会校验 SHA-256）：27 层 ViT，带 2x2 merger，
与 Flash-Next 模型的投影器（projector）属于同一族（`qwen3vl_merger`；只有输出宽度不同：这里是 2048，那边是 2560）。Strata
用同一个辅助程序（`strata-vision`，即 llama.cpp 的 `mtmd`）运行它，所以编码器的选项就是 Flash-Next 的那一套
（[图片](DETAILS.md#images-vision)）。图片默认开启，规则与 NVIDIA 和 AMD 卡上的每个模型相同：
显存低于 24 GB 时用 CPU 读取器（每张图几秒，不占显存），24 GB 起用卡的读取器（GPU 编码器，
最多 1,024 图像 token 时约占 1.2 GB 显存；在 AMD 上它是 `strata-vision-hip`，以 CPU 读取器作为回退）。
`--vision yes|no|gpu|cpu` 和 `--vision-tokens N` 的用法与那里相同；你要求什么就保留什么，并附一条说明。Mac 引擎
不运行这个模型。

| 编码器 | 每张图的时间（640x400 = 260 token / 800x450 = 350 token） | 显存 |
| --- | --- | --- |
| GPU，RTX 3060 | 0.10 s / 0.15 s | 最多 1,024 token 时 1,179 MiB（2,048 时 1,337 MiB），含 CUDA context |
| CPU，32 线程（R9700 机器） | 0.9 s / 1.1 s | 无 |
| CPU，10 线程（3060 机器） | 1.6 s / 2.1 s | 无 |

一张图最多变成上下文里的 1,024 个 token（CPU 默认是 300）。引擎把编码器的各行放到 prompt 中
`<|image_pad|>` token 所在的位置，并给每一行它的二维位置，M-RoPE 交错方式与 llama.cpp 对这个模型的做法完全一致（旋转区段
11 / 11 / 10，一张图的行位于 (t, h, w) = (p, p + row, p + column)，其后的文本从 p + max(columns, rows) 继续）。

**与 llama.cpp 对照检查**（用它的 `mtmd` 和它自己的图，两边编码器都跑在 CPU 上，prompt id 相同，把
llama.cpp 给出的答案喂给两边、从而逐步比较 logits，共 24 步；“floor”指 llama.cpp 的 CPU 后端对它自己的
HIP 运行，也就是两个正确的引擎在这个模型上的噪声水平）：

| 图片与问题 | prompt token | 第一个 token | 平均 KL，llama.cpp HIP 对 Strata | floor（llama.cpp CPU 对 HIP） |
| --- | ---: | --- | ---: | ---: |
| 640x400，图中有文字 | 288 | 相同 | 0.029 | 0.056 |
| 640x400，列出图形 | 294 | 相同 | 0.035 | 0.039 |
| 800x450，图中有文字 | 378 | 相同 | 0.021 | 0.031 |
| 800x450，描述图形 | 381 | 相同 | 0.0005 | 0.0019 |
| 1024x1024，标题（1,024 个图像 token，分 3 个分块读入） | 1,042 | 相同 | 0.0022 | 0.0026 |
| 一个请求里两张图，各自的文字 | 655 | 不同（几乎打平：这一步 floor 的 KL 也是 0.16） | 0.014 | 0.022 |

回答的文本与 llama.cpp 相同：`STRATA 42`（llama.cpp 自己的写法是 ` STRATA42`）、`CODE 4217`、`Red circle / Blue square
/ Green triangle`、`A red square is positioned on the left ... A blue circle is positioned on the right ...`。打开图片相关
选项后，不带图片的请求给出的 token 与不开时相同（10 个 prompt x 128 个 greedy token，完全一致）。

图片在与同时多个请求、MTP 草稿以及会话缓存一起用时都能工作：同一个会话再次发送（聊天应用会重发它的图片）时，
只要图片相同就从保留的状态继续（图片按服务器为每张图计算的 key 匹配）；换一张图则会话重新开始。

## 同时多个请求
<a id="several-requests-at-once"></a>

模型配置里的 `"parallel": N`（`strata-qwen36-<size>.json`，或 setup 时的 `--parallel N`）让引擎保持 N 个会话打开
（`--batch N`，最多 8 个）并把它们一起 decode：每个窗口带每个会话的一个 token，于是稠密权重、输出头和
两个会话共享的每个路由专家层，对所有这些会话只需读一次。服务器无需改动：它说的是与 Flash-Next 相同的引擎协议
（[BATCHING.md](BATCHING.md)）。在另一个请求正被读取时到达的请求只需等这一次读：新请求的 prompt 在其它请求的
decode 窗口**之间**读入，而会话在持有其起始状态的槽位里继续（或者由引擎从别的槽位复制更长的保留起始状态）。
一个 3,008 token 的 prompt 用 0.95 s 读完（3,200 tok/s，6 个分块），旁边有三个正在 decode 的槽位：
每个槽位最多停顿 160 ms（一个分块），而不是整次读，其间还产出了 20 个 token（每个分块一个窗口，即默认设置）；
`STRATA_Q36_READ_WINDOWS=4` 让它们在 1.14 s 的读里产出 65 个 token（占用更多时间，读更慢）。
一个独自运行的请求（solo 通路，带它的 MTP 草稿）在有别的请求到达时被移进批量槽位、在重新独自运行时又移回，
给出的文本与它独自运行时相同（服务器的移交复用保留的状态）。

总 decode 速度，同时 N 个请求，相同 prompt，greedy，每个 128 个新 token，墙钟时间从第一个请求到最后一个
回答，**R9700 32 GB，UD-Q4_K_XL，llama.cpp `llama-server -np N`**（5 对交错，中位数；Strata 用 `--batch 8 --mtp 0`）：

| 同时请求数 | Strata | llama.cpp | 比值 | 更快的对数 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 83.9 tok/s | 73.8 | 1.14 | 5/5 |
| 2 | 173.5 | 107.4 | 1.61 | 5/5 |
| 4 | 252.0 | 165.0 | 1.53 | 5/5 |
| 8 | 325.4 | 208.1 | 1.56 | 5/5 |

**RTX 3060 12 GB，UD-Q4_K_XL 用 hybrid 模式**（每个引擎都配它需要的槽位：`--batch N` 会占走专家槽位的空间；llama.cpp
用 `llama-server -np N -ncmoe 28 -t 8`，这是在这张卡上做扫描得到的最佳切分；5 对交错，中位数；这台机器
在运行之间还跑别的任务，但运行期间从不如此）：

| 同时请求数 | Strata | llama.cpp | 比值 | 更快的对数 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 64.0 tok/s | 41.1 | 1.56 | 5/5 |
| 2 | 85.1 | 52.5 | 1.62 | 5/5 |
| 4 | 99.3 | 63.0 | 1.58 | 5/5 |

在 2、4、8 个槽位、在 decode 槽位旁读入 2.5K token 的 prompt、槽位被后续请求复用、带图片以及带采样（相同 seed）
等情况下，每个槽位的 token 都等于同一请求独自运行（即基础引擎）时的 token。通过服务器：四个并发的聊天
请求给出的文本，与这四个请求依次执行相同。

**MTP 草稿。** 独占引擎的请求保留它的 MTP 草稿（没有别的东西在跑时，服务器就单独发它）。有
多个请求时，批量窗口没有草稿，除非配置的 `args` 里有 `--batch-mtp`（需手动开启）：此时每个槽位的窗口还
带上它的 MTP 块给出的提议（每个槽位一个，上限是 8 行窗口里空余的行数），而被确认的提议会让
窗口往前走两个 token。相同 prompt，5 对交错，R9700：

| 同时请求数 | `--mtp 0` | `--mtp 2 --batch-mtp` | 比值 | 更快的对数 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 83.7 tok/s | 134.0 | 1.60 | 5/5 |
| 2 | 173.1 | 207.0 | 1.20 | 5/5 |
| 4 | 251.0 | 275.0 | 1.10 | 5/5 |
| 8 | 324.0 | 320.5 | 0.99 | 0/5（没有空余行：没有提议） |

加与不加，文本都相同（每个槽位都等于它 solo 时的 token）。

**一个槽位的代价。** 每个槽位在显存里保留自己的缓存：上下文 32K 时 1.5 GB（10 个 attention 层
和 MTP 块的 fp32 key 与 value，每 token 45 KB）加上 0.07 GB 的循环状态。setup 为一个会话写上下文，
所以 N 个槽位要从本来给专家层的空间里占去 N 倍：在装不下全部专家层的卡上（12 GB 和 16 GB，即 hybrid 模式），
这就是专家槽位损失的空间，而批量会从内存里读到更多不同的专家层。setup 只在会话不会吃掉专家层空间的地方
**提供 `--parallel`**：在所有专家层仍能装下时最多 3-4 个（32 GB 卡在
32K 下是 3 个）；在装不下的卡上（hybrid 模式）则取会话占用不超过“本来给专家层的空间的 35%”的槽位数，所以它
取决于你选的上下文（12 GB：8K 时 4 个槽位，32K 时没有；16 GB：32K 时 2 个槽位）。它会同时报出代价，问
“How many requests at once?”（回车即保持一次一个），你给的任何数字都会被保留。在 hybrid 卡上实测（UD-Q4_K_XL，5
对交错的中位数，`--mtp 2` 按 setup 写入的方式；“一起”指 N 个并发请求的每秒总 token 数，对照的是带草稿层时一次一个请求）：

| 卡、上下文 | 槽位 | 单个请求独自运行，对比 1 个槽位 | N 个一起，对比一次一个 |
| --- | ---: | ---: | ---: |
| RTX 3060 12 GB，8K | 2 / 4 / 8 | -3.5% / -4.3% / -12% | 0.99x / 1.15x / 1.10x |
| RTX A4000 16 GB，32K | 2 / 4 | -10.6% / -29.9% | 1.03x / 0.76x |
| Tesla P100 16 GB，32K | 2 / 4 | -7% / -23% | 0.98x / 0.81x |

不用草稿层（`--mtp 0`）时，同样的槽位一起运行给出 1.26-1.64x（3060 在 8K：4 个槽位 1.64x，代价是独自运行时 -5.5%），但单个请求
带草稿本来就比不带快约 1.6x，所以在小卡上主要收益是第二个用户能同时开始；
速度收益不大。在装得下全部专家层的卡上（R9700 32 GB，8K prompt）4 个槽位是一带草稿的一次一个的 1.45x（用
`--batch-mtp` 时 1.59x）。引擎在分配之前会说明会话要占多少，并（连同数字）拒绝一个装不下的槽位数。

在 hybrid 模式下，一个请求的文本在独自运行与在旁边有别的请求时可能略有差异：待在 GPU 上还是
CPU 上的专家层会随所有请求的路由而变，而两者的计算舍入不同。把槽位表固定（`STRATA_Q36_FIXED_SLOTS=1`，一个测试设置）后，在那种情况下
每个槽位也等于它 solo 的运行，无论有没有 `--batch-mtp`。

## 速度（0.1.45）
<a id="speed-0145"></a>

这条引擎通路上的 decode 和 prompt 内核为了速度被重写过；**decode 通路上的每一处改动都给出旧内核的位**
（`STRATA_Q36_VERIFY=1 strata ... --no-graph` 会在真实激活值上把旧内核放在每个新内核旁边运行并逐位比较：
在 R9700 和 RTX 3060 上的 18,360 / 8,187 / 6,399 次比较中 0 处不一致；`STRATA_Q36_OLD_KERNELS=1` 会把它们全部关掉）。这
10 个 parity prompt（greedy 128）给出基础引擎的 token，不带和带 `--mtp 2` 都是。凡 prompt 的分块大小发生变化的地方，数字
会略有变化：见“prompt 分块”一节。

**慢在哪里**（rocprofv3，R9700，UD-Q4_K_XL，纯 decode，每 token 11.25 ms 内核时间）：大的 Q8_0 乘法（attention、
GDN 投影、输出头：每 token 1.9 GB）跑到 530 GB/s，已是内存带宽上限。其余没有：共享专家层和 attention 的 k/v 乘法
（每 token 140 次）耗时 18 us，Q4_K gate/up 内核只跑到 250 GB/s，`k_moe_out`（一个块）17 us，`k_group`
（一个线程遍历 256 个专家层）9 us。现在：这些乘法改成每行一个 warp（在 gfx1201 上，2048 个 warp 的一次启动耗时 21 us，
而 1024 个 warp 只用 5 us，所以对 grid 做了上限），共享 gate+up+SwiGLU+q8_1 合成一次启动，MoE 结尾
用 1024 个线程并处理下一层的 q8_1 镜像，add+norm+q8_1 合成一次启动，router top-k 与分组
合成一次启动，router 与共享 gate 合成一次乘法，Q4_K gate/up 用 V2K 内核（`STRATA_EXPERT_V2K`，gfx12 上默认）。
prompt 的 GDN conv 以 16 个 token 为一组并行分块运行，delta rule 提前一个 token 加载、每 token 两个 barrier（两者都是精确的）。

R9700 32 GB（p620，HIP gfx1201），UD-Q4_K_XL，base = 本次工作之前的引擎，5 对交错，每对重复 3 次，中位数；llama.cpp
972b5fc HIP 在同一文件上（`-fa 1`，`-ub` 512 / 2048 中取较好者）：

| | base | 0.1.45 | 比值 | 更快的对数 | llama.cpp |
| --- | ---: | ---: | ---: | ---: | ---: |
| decode tg128 | 83.2 tok/s | 117.8 | 1.42 | 5/5 | 81.9-82.1 |
| prompt pp4096 | 3,453 | 6,220（分块 4096） | 1.80 | 5/5 | 3,794 (-ub 2048) / 3,042 (-ub 512) |
| `--mtp 2`，10 个 prompt greedy 128 | 167.7 | 183.7 | 1.10 | 3/3 | 129（draft-mtp，n-max 2，更早的运行） |
| 同时 1 / 2 / 4 / 8 个请求（`--batch 8 --mtp 0`） | 85.2 / 182.4 / 271.9 / 361.1 | 122.4 / 205.1 / 303.3 / 386.9 | 1.44 / 1.12 / 1.12 / 1.07 | 5/5 | |

同一张卡上的 UD-Q6_K_XL（每个主层的专家层都在显存里，所以 prompt 分块保持 512）：decode 80.4 -> 106.9 tok/s（1.33），pp4096
2,160 -> 2,200（llama.cpp 在 -ub 2048 时为 3,486，在 -ub 512 时为 2,738；decode 81.1），`--mtp 2` 154.7 -> 167.3。那里用 `--chunk 2048` 会把专家层
移到 hybrid 布局（每层 256 个中有 205 个在显存里）：prompt 3,500 tok/s，decode 94 —— 这是一个选项，不是默认。

RTX 3060 12 GB（P2003，CUDA sm_86，20 线程），UD-Q4_K_XL 用 hybrid 模式（每层 256 个专家层中有 37 个在显存里）：一个
token 的 GPU 部分是卡带宽下的稠密 Q8_0（17 ms 中的 6 ms），其余在等 CPU 池（专家层占 9 ms），所以只有小
内核那部分的份额有收益：decode tg128 58.5 -> 59.7 tok/s（+2%），pp2048 1,958 -> 2,022（+3.3%），10/10 一致，不带和带 `--mtp 2`
都是（84.3 -> 84.7）。llama.cpp 972b5fc CUDA（`-ncmoe 26 -t 8 -ub 2048`）：pp2048 1,328，tg128 48-52。

**prompt 分块（默认值改了）。** MoE 的 prompt 内核每个分块把每个专家层读一遍，所以分块越大，喂给它们的每个
专家层的行数就越多：R9700 上 pp4096 在分块 512 / 1024 / 2048 / 4096 时为 3,453 / 4,786 / 5,766 / 6,223 tok/s。当所有专家层都在显存里时，
引擎现在取 4096 / 2048 / 1024 中最大的、能放在专家层、0.77 GiB 预留和会话缓存旁边而不必让出
量化打包的 decode 副本的那个（8K-64K 上下文：4096，100K：2048，131K：512；`--batch 2..4`：最多 1024，这样别的槽位
不会被一整个分块占住，`--batch 8`：512）。hybrid 模式保持 2048（更大的分块会占专家槽位：RTX 3060
分块 4096 读 prompt 快 5%、decode 慢 13%），并在空闲 7.5 / 5.5 GiB 的卡上降到 1024 / 512。**`--prefill 512`（或
`STRATA_Q36_CHUNK=512`）给出旧的大小，那时文本逐位等于基础引擎。** 分块大小会改变 BLAS 选的 GEMM tile，
也改变 prompt 状态的最后几位：在六份真实的 1.5-3.2K token 文档上与 512 分块相比的 KL（每份 48 行 teacher forcing）：分块 1024 为 4.0e-3，2048 为 4.2e-3，
4096 为 3.6e-3（各 prompt 为 2.3e-3 .. 5.9e-3），top-1 一致为 48 行中的 44-48 行 —— 这与同一文件上
llama.cpp 的 CPU 对 HIP 差异（4.2e-3）量级相同，不是质量损失。在那六份文档之后 greedy 64 个 token：默认分块
在 6 份中有 2 份给出基础引擎的文本，`--prefill 512` 则是 6 份中的 6 份。比一个分块还短的 prompt（第一个之后的每个聊天回合）无论哪种都是一个分块：不变。
维护者保留新默认值的参考输出（六份文档，greedy 64），并用它们检查后续改动。

**试过但放弃的。** 把 MTP 草稿的头放在词表的一个子集上（`--draft-vocab N`，作为需手动开启的选项保留；答案从不
改变）：前 16K-131K 行在英文和代码上快 5-8%，但在中文 / 俄文 / 阿拉伯文 / 印地文上慢 10-15%（一个中文 prompt 的 token id 有
70% 在 65,536 以上），而用目前已见 token 构建的候选列表两边都更差。共享专家层放在第二条 stream 上
（被捕获进 decode 图）在这套 ROCm 下 decode 只有 36 tok/s 而不是 117。分块的（WY）GDN 和 PCIe 辅助的 hybrid decode
没有尝试。

## 未做 / 限制
<a id="not-done--limits"></a>

- 最多八个槽位（窗口持有 8 行）；`--batch-mtp` 在这些行之间分配给槽位和提议。
- 批量中的采样请求每个窗口 decode 一个 token，不带提议。`logit_bias` 在这条引擎通路上不可用：
  服务器会拒绝带它的请求（对 Flash-Next 的 `--batch` 也是如此）。
- 一个不再独自运行的槽位只能通过服务器自己的移交回到 solo 通路；MTP 块的缓存里，
  槽位在批量窗口中 decode 过的 token 处留有空洞（之后某段 solo 的草稿会稍差；文本不受影响）。
- Intel Arc（SYCL）不运行这个家族。
