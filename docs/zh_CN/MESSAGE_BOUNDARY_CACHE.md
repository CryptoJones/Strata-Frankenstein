# 在最后一条用户消息被编辑时复用长聊天历史
<a id="reuse-long-chat-history-when-the-last-user-message-is-edited"></a>

## 为什么有帮助
<a id="why-this-helps"></a>

agent 可以保持同一段很长的历史，只替换最后一条用户消息。
此时最终的缓存状态不再匹配，而最近的周期性检查点可能落在很后面。
引擎于是会重读它已经处理过的历史。

这一可选（opt-in）改动在上一轮边界处、也就是最终那条短消息之前，多保存一个检查点。
它使用现有的有界缓存，并让常规的 token 与图像前缀校验负责判断能否复用。

## 使用与限制
<a id="use-and-limits"></a>

在启动引擎前设置 `STRATA_CACHE_MESSAGE_BOUNDARY=1`。
它默认关闭，需要提示词缓存和一个有效的轮次 token，并且
只选择至少 8,192 token 的前缀、尾部最多 1,024 token。
层切分执行被排除（`multi_gpu`）；helper 专家 GPU 仍可用。
它可能会拆分 prefill 块，并给全新请求增加快照开销。

## 验证环境
<a id="validation-environment"></a>

- 两块改装过的 RTX 3080 20 GB 显卡；CUDA SM86、CUDA 13.1、Linux。
- Intel Xeon E5-2686 v4（18 核 / 36 线程），可用 RAM 约 94 GiB。
- PCIe 3.0，GPU 之间无 peer-to-peer 访问；17 个专家池 worker。
- Qwen3.8-Flash-Next IQ3_S，131,072 token 上下文，INT8 KV，
  32,768 个常驻 KV cell。
- Medium thinking：2,048 token 的推理上限，8,192 token 的输出上限。
- 物理 GPU 功耗上限保持在 250 W 和 280 W。没有提高功耗。
- 历史性能测试使用的是基于官方 v0.1.38 加经评审的 architectds/Strata 改动（最佳为 05c0f36）的隔离引擎。
  本 PR 只包含我们的改动，已移植到官方 main（99f3dbd）。
  历史计时并非对这个纯上游移植版的实测加速。

## 历史收益
<a id="historical-benefit"></a>

相同二进制下的 ABCCBA 对比，每个变体两次重复：

| 指标 | 按需边界 + 16K 块 | 预判边界 + 32K 块 |
| --- | ---: | ---: |
| 首次完成 100 条记录的编辑 | 17.236 s | 11.527 s |
| 三次完整编辑 | 41.266 s | 35.802 s |
| 冷启动加三次编辑 | 58.688 s | 53.146 s |
| 十一个用例的墙钟时间之和 | 133.844 s | 127.983 s |

首次编辑的时间下降了 33.1%；复用的前缀从 22,016 增长到 32,831 token。
这是一次**合并**的边界策略与块大小对比，而不是把这个检查点加到纯净上游上所带来的隔离收益。
热生成没有变化（97.55 对 97.60 tokens/s）。
混合用例的缩减为 4.4%；普通的冷 8K 请求多花约 0.2 s。

历史对比通过了 77 项任务/缓存检查以及取消/恢复。
为所采用的 32K 选择单独做的一组安全检查通过了 22 项任务/缓存检查，
包括 120K、图像历史隔离和取消/恢复。

## 验证与相关工作
<a id="validation-and-related-work"></a>

- 独立的 selector 测试通过全部 21 个用例，且没有在 Release 构建中会消失的断言。
- 针对纯官方 main（99f3dbd）的 Linux 编译/链接通过。没有启动引擎，也没有改动任何生产设置。
- PR #614 在不拆分某个块的情况下，为尾部附近一个已经到达的块建立检查点。
  本方案选择一个消息边界，因此可能拆分块。两者以不同的代价和数值权衡解决相关的场景。
- 块的几何形状会影响浮点结果。没有声称纯上游的逐位
  一致性或隔离的上游加速。在验证通过之前保持 draft。
