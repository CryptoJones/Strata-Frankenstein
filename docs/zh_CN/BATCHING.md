# 同时处理多个请求（批量槽位）
<a id="several-requests-at-once-batch-slots"></a>

没有并行选项时，Strata **一次只服务一个请求**：其他请求在服务端队列里等待。有了 `"parallel": N`
（引擎的 `--batch N`，也可写作 `--slots N`），引擎会最多保持 N 个对话处于打开状态并**一起**解码它们：
于是每个 verify window 携带每个对话的一个 token，所以稠密权重、共享专家、输出头，以及两个对话共用的
每个路由专家，对它们全体而言每个 window 只读取一次。再配合跨多块 GPU 的层切分与 `--batch-groups`，
各块卡也会同时对不同对话工作，而不是互相等待。

上游把它保持为可选开启，且在这些选项缺席时不改动任何东西（#465；引擎部分是 PR #559）。在本 V100 fork
中，setup 会为新的 Volta 配置写入 `"parallel": 2`。它会保留已有的 parallel 设置。用 `--parallel 1`
禁用它。当两个槽位放不进显存时，引擎可以回退为一次一个请求；请检查 `/v1/status` 中的
`concurrency.serving`。额外的槽位可能降低单请求速度。

**Qwen3.6-35B-A3B** 在它自己的引擎路径上有同样的选项（`"parallel": N`、`--batch N`、`--batch-mtp`，
最多 8 个槽位，相同的引擎协议与相同的服务端）：它的数字、一个槽位的代价，以及 setup 在哪里推荐它，
都在 [QWEN36.md](QWEN36.md) 中。

## 开启它
<a id="turning-it-on"></a>

单块 GPU：在模型配置（`strata-<model>.json`）里加上 `"parallel": 2` 并重启，或者用 `--parallel 2`
运行 setup。setup 只在不会牺牲速度的地方推荐它（见下文）。你要求的任何数字都会照原样保留，只有当它
超过 setup 会推荐的数量时附注一句。

```
"parallel": 2
```

配合 MTP（`--mtp` 与 `--spec`）时，`--batch-mtp`（写在配置的 `args` 里，或在服务端环境里设
`STRATA_BATCH_MTP=1`）让每个批量槽位在每个 window 校验一个 MTP 提案。它是可选开启的；没有它时，下文
描述的批量行为与不带 MTP 时完全一致。它需要每个槽位为草稿状态与缓冲区保留显存，所以在较小的卡上使用
前请先查看引擎的空闲内存日志。当它无法运行时（只有一个槽位、没有 `--mtp`、带 `--batch-groups` 大于 1
的层切分，或带助手 GPU 专家缓存或 `--remote-expert-opt` 的层切分，或两级放在一块 GPU 上的层切分），
引擎会说明原因并按常规方式批量运行。RTX PRO 5000 的用户实测在单块 GPU 上带 2 到 4 个客户端时总吞吐
提升 +31% 到 +39%（也有一次 RX R9700 的运行）。

**配合层切分**（例如两块 GPU 上的 `"layer_split": "24"`、`"parallel": 2`、`--spec 4 --mtp ...`）
它的工作方式相同，只是各槽位的草稿器放在**最后一级所在的 GPU** 上（单独草稿器与输出头也在那里）：
每个槽位得到一个草稿器，它共用单独草稿器的权重，只拥有自己的 K/V 环形缓冲与缓冲区（引擎会在启动时记录
`--batch-mtp: N slot drafters on CUDAk (X MiB ... each)`；每个槽位的 K/V 环形缓冲也保留一份页锁定的
内存副本，与单独草稿器一样）。一个 window 会让每个活跃槽位的两行（它的 token 与它的提案）穿过每一级，
所以一个 window 中最多有四个槽位；更多的槽位（`--batch` 取放得下的数量）轮流经过。各 window 依次
穿过各级（`--batch-groups 1`）：在 0.1.41 上，`--batch` 为 2 或以上的层切分默认会把槽位按组分组成
流水线，而流水线路径不运行槽位的 MTP 草稿，所以在 `--batch-mtp` 且没有 `--batch-groups` 时，引擎
（0.1.43.1）会走流水线并保持 `--batch-mtp` 关闭，并说明这一点（0.1.42/0.1.43 会用它运行一个串行组：
在 2x A4000 上 4 条流的合计为 63.9 tok/s，流水线为 91.8，不带 `--batch-mtp` 的流水线为 85.8；#2038）。
`--batch-groups 1` 或 `STRATA_BATCH_MTP_SERIAL=1` 会保留 `--batch-mtp` 并使用串行 window，按下面的
实测，约两条流时这是更好的选择；命令行给出的 `--batch-groups G`（G 大于 1）或 `--batch-groups auto`
会保留流水线并关闭 `--batch-mtp`。只有两级放在两块 GPU 上的层切分被实际运行过。

在 2x RTX 3080 20 GB（220 W 上限）配 Xeon E5-2696 v4、UD-Q4_K_XL、`"layer_split": "23"`、
`"parallel": 2`、`--spec 4` 的层切分上实测：两个并发的贪心 decode 各 300 个 token，两条流的 tok/s
相加，取测量值的中位数（每次重启引擎后跑 10 轮两条流，每次重启 20 个测量值）。引擎是 0.1.41 且带有我们
其余的生产栈（共享 KV 池，以及在前两个分支中批量 window 内运行自适应专家层；第三个分支的流水线路径从不
在 window 内自适应），所以这是在那套栈之上的 `--batch-mtp`，不是单独这一改动跑在上游主干上。

| 分支 | 合计 tok/s | 重启次数、测量次数 | 每 window |
| --- | --- | --- | --- |
| `--batch-mtp`，一个组 | **89.2** | 3, 60 | 3.3 行，34.6 ms，66-67% 的提案被接受 |
| 无 `--batch-mtp`，一个串行组 | 77.3 | 2, 40 | 2.0 行，23.7 ms |
| 无 `--batch-mtp`，`--batch-groups` 未设（0.1.41 的默认：两个流水线组，每组一个槽位） | 77.7 | 1, 20 | 每个流水线组一步一行 |

即 `--batch-mtp` 相对不带它的串行 window 提升 +15.4%（中位数之比的 95% bootstrap 区间为 +12.5% 到
+17.9%），相对流水线默认提升 +14.8%；不带它的两个分支彼此持平。单条流本身带与不带它的 decode 速度相同
（81.7 与 82.0 tok/s），而两个槽位草稿器在最后那块 GPU 上花费 35 到 110 个专家缓存槽位（每个 50 MiB
的私有状态）。

流水线默认值在一点上更好：当一条流正在 decode 时到来约 48k token 的新提示词，流水线组下以 2508 tok/s
读取，串行 window 下是 1217 tok/s，且正在 decode 的那条流更早结束（整个过程中是 25.0 对 18.0 tok/s）；
`--batch-mtp` 不改变这一点。所以在并发 decode 占主导时它划得来；当长读取与 decode 同时发生时，流水线组
可能是更好的选择。未测量：超过两级（#1253 上的报告发现四级没有收益）、超过两个槽位、带采样的 decode，
以及上游主干的二进制（流水线分支是我们的构建，用 0.1.41 解析出的那些标志启动）。

我们在 2x R9700 且全部专家层都在显存中的层切分上对 `--batch-mtp` 的实测：相对流水线默认从 80.2 降到
62.7 tok/s（-21.9%，5 组配对中 0 组更快），所以只有当专家层不能全部放进显存时它才划得来。

更早，在引擎 0.1.40.3 带这一改动、同样两块卡、两条并发流上：UD-Q4_K_XL 不带 `--batch-mtp` 为 39.9 到
43.5 tok/s，带上为 44.5 到 51.3 tok/s（每个分支 2 次运行）；一个全部专家层都在显存中的小型 Coder IQ1_M
测试模型，不带为 84.0，带上为 101.2，两条流的贪心文本相同。

文本：在两个分支使用相同专家缓存的情况下（槽位草稿器要占用显存，所以除非调整保留量，缓存会有差异），
并带 `--pcie-frac 0`、`--adapt-every 0`，5 个短提示词在全部 6 组比较中，`--batch-mtp` 的贪心文本与不带
时相等（每个分支一次重启）。这是文本相等，不是逐位精确性的证明，而另一条流正在 decode 时读取一个
25k token 的提示词，在同一分支的两条完全相同的流之间也不可复现。

配合层切分时，引擎选项写进配置的 `args`：

```
"args": [ ..., "--batch", "8", "--batch-groups", "4" ],
"layer_split": "12,24,36"
```

| 选项 | 它做什么 |
| --- | --- |
| `"parallel": N` / `--batch N` / `--slots N`（通常是 2..8；带层切分时每组最多 8，见下文） | 最多 N 个对话拥有批量槽位；更多请求等待空闲槽位。每个槽位在切分的每块 GPU 上都获得自己的状态（像该级自身那样切出的会话：GDN 递归、QSA 的 K/V 与索引器、PLE 历史）。带分组的 MTP 时，如果内存允许，超过 8 个槽位可以在 8 行的 window 之间轮换。 |
| `--batch-groups G` | 带层切分时（默认：auto，见下文）：把 N 个槽位分成 G 组，像流水线那样流过各 GPU（GPU k 运行一个组时 GPU k+1 运行另一个）。G 必须能整除 N。1 = 所有槽位在一个 window 中，一块接一块地过 GPU。 |
| `--batch-groups auto` | 自 0.1.41 起层切分上的默认（不给 `--batch-groups` 即可）：引擎为每个 GPU 级流水线化一个组（取能整除槽位数的最大数量；4 块 GPU 上 8 个槽位 = 4 组每组 2 个）并说明这一点（`INFO batch_groups=G`）。`--batch-groups 1` 关闭它（所有槽位在一个 window 中，一块接一块）。实测，8 个客户端，相对单组的总 tok/s：4 x R9700 为 166 对 86，2 块 GPU 为 109 对 78，3 块 GPU 为 110 对 78。带 `--adapt-async 1` 且没有 `--batch-groups` 时默认是一个组（批量 window 之间运行的自适应层不会在流水线组中运行），日志会说明；带 `--batch-mtp` 且没有 `--batch-groups` 时流水线胜出而 `--batch-mtp` 被关闭（`--batch-groups 1` 或 `STRATA_BATCH_MTP_SERIAL=1` 会保留它）；与 `--batch-mtp` 一起给出的 `--batch-groups G` 或 `--batch-groups auto` 会流水线化各组并关闭 `--batch-mtp`，与 `--adapt-async 1` 一起给出时会流水线化各组并关闭 `--adapt-async`（流水线路径不自适应）。 |
| 显式 `--layer-split` | 每块 GPU 只加载它自己那些层的稠密权重。这是自动的。由此释放出来的内存可供专家缓存使用。 |

引擎从不拒绝一个它无法运行的数量：它会在日志里说明，并运行它能运行的部分——不带层切分时最多 8 个槽位
（一个 window 容纳 8 行；带层切分与流水线组时是每组 8 行），显存放得下多少个就多少个，或者当连两个都
放不下时一个也不用（一次一个请求）。服务端会读取引擎报告的数量（`INFO batch_slots=N`），
`GET /v1/status` 也会说明它（`concurrency.serving`）。

各槽位的会话是在主会话、原生输出头、logits 缓冲区以及 MTP 草稿层**之后**切出的，因此适配性检查看到的
是每块卡上真正剩下的内存（草稿层位于切分的最后一级）：放不下的数量会回退为更少的槽位，或者当连一个额外
会话都无法在每个级放下时回退为没有批量槽位（一次一个请求）。`fit` 并不意味着"切分能成功"：每个槽位还必须
为该级已预订的工作集留出空间——`--vram-reserve-mib` 保留量、提示词路径在不借用时自己的缓冲区（以及带
配置档时，足够大因而能把它们借出去的专家缓存，使借用的提示词永不必回退到自己的缓冲区）、后面各级的
verify window，最后一级的草稿头，以及一个可用的缓存下限——否则第一个请求会发现 GPU 已满并死在
`verify: instantiate: out of memory`。这个回退是在启动时决定的，不是请求进行到一半时以显存不足报错。
在本 fork 的两块 V100 上，于 524,288 token 上下文、20/28 层切分与 `"parallel": 2` 下验证：引擎报告了
适配性检查，服务端保持就绪且配置未被改动，而每个请求都走单独处理路径（`GET /v1/status` 显示
`concurrency.serving` 为 1）。接纳时的精确空闲显存数字在针对批量槽位分配归属的一处后续修复之后重新验证过；
最终数字在基准测试报告中。

本 fork 让上游的级权重裁剪对显式的 CUDA/HIP 切分自动化。请从那些配置中移除 `--trim-stage-weights` 与
`STRATA_STAGE_TRIM`；它们不再被接受也不再需要。独立的实验性 Intel（SYCL）引擎保留它自己的可选开启路径。

## 层切分上超过 8 个槽位，以及可选开启的接纳与 decode 开关
<a id="more-than-8-slots-on-a-layer-split-and-the-opt-in-admission-and-decode-switches"></a>

（来自 havok2-htwo 的补丁系列，PR #2364。）

**超过 8 个槽位。** 带层切分时，一个流水线 window 最多容纳 8 行，但流水线中的每个组都是它自己的 window，
所以 4 块 GPU 上的 `--batch 16` 运行 4 组各 4 个槽位（`--batch-groups auto`），`--batch 32` 运行
4 组各 8 个。到 0.1.44.1 之前，引擎会把这样的请求削减到 8 个槽位并说明；现在它会照要求运行，放入显存
放得下的槽位数，且每组最多 8 个（`INFO batch_slots=N`）。`--batch-mtp` 保留它的上限（提案会使每 window
的行数翻倍）。8 个槽位或更少的情况不变。16 槽位批量流水线中的每个槽位解码的 token 与它单独解码时完全一致
（`tools/batch_test.py --n 16`，它现在支持最多 32 个提示词）。

**可选开启的开关**（引擎的环境变量，即配置中的 `"env"`；没有一个默认开启）。每一个都只改变工作的调度或
拷贝方式，不改变计算的内容；`tools/batch_test.py` 会检查每个槽位解码的 token 与它单独解码时一致。

| 开关 | 它做什么 |
|---|---|
| `STRATA_SLOT_COPY_DIRECT=1` | 一次接纳（以及一个槽位的恢复）在设备之间直接拷贝运行状态与 QSA K/V，而不是经过宿主镜像 |
| `STRATA_SLOT_COPY_BATCHSYNC=1` | 配合上项：把约 116 次拷贝排队，并且每个设备只同步一次 |
| `STRATA_SLOT_CKPT_MOVE=1` | 接纳那一轮的轮次检查点移入槽位（不再有 112 MB 拷贝）；它还会像 `STRATA_CKPT_POOL` 那样保留被丢弃检查点的存储；接纳之后立刻执行的会话 SAVE 或取出的停放对话会缺少那个被移动的检查点（它由槽位持有） |
| `STRATA_CKPT_POOL=1`、`STRATA_CKPT_THREADS=1` | 检查点保存到某个被丢弃检查点的向量里；切分中各级的部分一次性保存 |
| `STRATA_ADMIT_MERGE_FIRST=1` | 一次接纳在一个 window 内读完它最后的提示词 token 与它的第一个 token（仅当全部专家层都常驻时） |
| `STRATA_PIPE_BYIELD_NODRAIN=1` | 抵达流水线批量的 BYIELD 会被直接丢弃，不排空各组 |
| `STRATA_BATCH_SELF_COMMIT=1` | 每槽位一行的 window 自行推进 GDN 状态，不使用提交图 |
| `STRATA_QSA_SLOTS=1` | 一个 window 的 QSA 块打分、top-k 与注意力在其各行上作为一次启动运行 |
| `STRATA_HANDOFF_PIPE=P` | 层切分把一个提示词分块分成 P 段（2..16）交给下一块卡，由事件做门控，在一个常驻线程上 |
| `STRATA_ADMIT_SHORT_FIRST=N`（服务端） | 最多 N 个 token 的新提示词比更长的提示词优先走控制线（等待超过 `STRATA_ADMIT_MAX_WAIT_S`，默认 30 的更长提示词算作短提示词） |
| `STRATA_TRACE=1` | 每次接纳输出一行，含其各阶段（排空、提示词、首个 window、槽位拷贝、检查点拷贝） |
| `STRATA_MMQ_DIRECT=1`、`STRATA_MMQ_GROUP_SORT=1` | CUDA，需要构建选项 `-DSTRATA_MMQ_TAB=ON`：提示词 MMQ 就地在缓存槽位中读取常驻专家；完整的 MMQ 组按行数排序（docs/DETAILS.md） |

每个槽位的会话要从专家缓存那里占用显存，所以在专家层不能全部放下的单卡或切分上，16 个槽位会牺牲单用户的
速度（一个槽位的代价见上面各节）。

### 一个槽位的代价，以及 setup 的推荐
<a id="what-a-slot-costs-and-what-setup-recommends"></a>

每个槽位的会话都要占用本可被专家缓存持有的显存：32K 上下文配 8-bit KV 时是 0.56 GiB，上下文更长时更多，
除非 KV 缓存流式化（`--kv-resident`：那样只有注意力的 32K 窗口留在显存中，而每个槽位整份 KV 缓存占用
页锁定内存——128K 时是 1.6 GB）。在本 fork 的两块 V100 上，32,768 token 上下文的 20/28 切分上，
槽位会话实测为 0.24 GiB（第一块卡）与 0.33 GiB（最后一块卡）。在 524,288 token 上下文的 24/24 切分上，
每个槽位每块卡需要 3.66 GiB。在接纳逻辑修复之前，两个这样的槽位会留下不足的工作内存，导致第一个请求失败。
修正后的引擎在实测过的 20/28 与 24/24 切分上，同时开启视觉与 MTP 时都是一次一个请求。在一块其专家层大多
跑在 CPU 上的显卡上，一个批量读取的不同专家数量与逐个请求读取的大致相当（不同的对话会路由到不同的专家），
所以收益在**等待时间**上（没有人要等一整个回答），而单个请求独自运行反而更慢（专家缓存更小）：
12 GB 卡上是 11-24 %，见下文的实测。

因此 setup **只在专家层大多能放进显存的地方**推荐 `"parallel"`：专家缓存（每块卡的显存减约 5 GB，
层切分时把每块卡都计入）在槽位之外仍须至少持有模型一半的专家，且槽位最多占用它的五分之一，上限 4 个槽位。
以 32K 的 Q2_0 计算，24 GB 卡上是 3 个槽位，32 GB 起或像 2 x 16 GB 这样的切分上是 4 个；IQ3_S 需要
32 GB 或一个切分。其他所有情形（任何单独的 12 或 16 GB 卡）都保持一次一个请求，setup 会说明：
"parallel N reduces waiting for several users but costs about 10-25% speed per request on this card"。
无论哪种情况，`--parallel N` 都会照你要求的生效。

## 服务端如何使用槽位
<a id="how-the-server-uses-the-slots"></a>

- **单独一个请求**走常规的单独处理路径（带 MTP 草稿的 verify window）：最快的单流。
- **当第二个请求到来时**，第一个会被停止（`STOP`）并在一个批量槽位中带着它的提示词加上它至此生成的内容
  继续——引擎的提示词缓存恰好保存着那些内容，所以任何东西都不必重新读取——新请求被接纳到它旁边。默认情况下，
  槽位中的请求**不带 MTP 草稿**解码（每个 window 一个 token）。有了 `--batch-mtp`，每个槽位在当前 token
  旁边校验一个 MTP 提案。
- **一个被独自留在槽位中的请求**（其他都结束了，没有人在等）会回到单独处理路径：该槽位被停止，引擎把它的
  各会话拷回并带着 MTP 草稿再次解码（每个请求最多两次；带 `--prompt-cache 0` 时会留在槽位中；
  `STRATA_PARALLEL_SOLO=0` 关闭该行为）。草稿层自身的 K/V 那时是为另一个对话构建的，但实测它接受的草稿数量
  （172 个中 140 个）与读取了该对话的草稿层一样（173 个中 140 个）。
- **超过槽位数的请求**等待空闲槽位（`/metrics` -> `live.slots` 会显示每个槽位：空闲、读取中或解码中，
  以及它的 token 数与 tok/s；`live.running` 是在途请求数）。
- **每次接纳**都通过常规的提示词路径读取该请求的提示词（包括提示词缓存与对话检查点），并在该路径上产出它的
  第一个 token；随后状态被拷入槽位。接纳一次只做一个，而**槽位会在提示词各分块之间解码**：每个分块之后
  （`--prefill`，2048-8192 个 token）它们解码该分块耗时的一半那么长（`STRATA_BATCH_DECODE_SHARE`，
  默认 0.5），所以一个长提示词会拖慢其他请求，而不是让它们停下来。各分块就是一次不间断读取会用到的那些，
  所以提示词的算术不变。
- **长提示词会为短提示词让路**（#656 的协作式抢占）：当一个提示词长度不足其一半的请求在等待时，服务端会
  发送 `BYIELD`；在下一个分块边界处，长读取停止，已读取的部分被拷入一个槽位，短请求被接纳，随后长请求带着
  同样的各分块从它的槽位继续（每个请求最多两次）。
- **每个槽位都是一份对话缓存。** 一个结束的槽位会保留它所持有的内容（提示词、回答，以及提示词最后一个轮次
  边界处的检查点）；该对话的下一轮会交给那个槽位，引擎把它的状态拷回（一段短对话约 50-60 ms），而不是重新
  读取历史——对于一个从历史中丢弃回答思考部分的客户端也是如此（检查点与新轮次之前保持一致）。新对话取一个
  空槽位，否则取最久未使用的那个。
- 在内存缓存、磁盘层与各槽位之间，以请求提示词的最长有效前缀为准：更短或等长的磁盘记录不会挤掉一个空闲槽位
  返还的更长状态（一次返还本来就已常驻；等长的记录只会多花一次读取与一次恢复）。在本 fork 的两块 V100 上
  以三个槽位验证：一条 25 token 的磁盘记录没有挤掉 152 token 的状态，一条 172 token 的记录也没有挤掉
  299 token 的那个。
- 槽位的分配方式使连续的请求落在不同的流水线组中（`--batch-groups`）。
- 断开的客户端会停止它的槽位（`BSTOP`）；其他槽位继续。

## 与流水线组并行读取提示词（实验性，可选开启）
<a id="reading-a-prompt-beside-pipelined-groups-experimental-opt-in"></a>

带层切分且 `--batch-groups` 大于 1 时，一个提示词会在一次运行中读完：每个正在 decode 的槽位都会停下来
直到它读完，无论它有多长（#1906）。单块 GPU 没有这个问题：那里槽位会在提示词各分块之间解码
`STRATA_BATCH_DECODE_SHARE` x 该分块的耗时。

`STRATA_PIPED_CONCURRENT=1` 会在一个自己的线程上读取提示词，同时各槽位组继续通过流水线解码，而不是让它们
停下：提示词的各分块与各槽位的 window 同时运行在同样的 GPU 上，各自用自己的流（在 CUDA 上，各 window
的流置于设备的最高优先级；`STRATA_PIPED_CONCURRENT_PRIO=0` 保持默认），于是各槽位从不等待这次读取，
而这次读取仍是一次内部不含排空的运行。

- 提示词的 K/V 交给主会话，各槽位的交给它们自己的，所以它们不会触碰彼此的状态。它们都要读取的 n-gram
  （PLE）表会被加锁。自适应显存层在读取期间保持静止：它的那一轮落在读取之前，且读取运行时不会开始新一轮。
- 提示词路径借用的显存专家槽位会在读取之前借出、读取之后重新填满，期间没有在途操作；在这两者之间，各槽位的
  window 在 CPU 上计算这些专家层。
- 读取期间，各槽位的门铃由一个自己的线程服务，该线程不做任何 CUDA 调用。一次 CUDA 调用可能要等驱动的锁，
  而持锁者可能在等 GPU——一次空闲，或是第一个新形状内核要加载的模块——而该 GPU 上的一个 window 又在等它的
  门铃（issue #31 的那个模式：在构建此功能期间发现了两处这样的挂起，并从引擎的停顿转储中读出）。MTP 草稿器的
  提示词缓冲区与提示词路径的页锁定上传槽位会在读取之前定好大小，所以它的线程不分配也不释放任何东西。在各 window
  之间，门铃线程等待下一次启动来唤醒它（一次定时睡眠在 Windows 上是一整个定时器 tick，最多 15.6 ms）。
  一个永不结束的 window 仍会被发现（它的图在还差一层未响铃时结束，或者 20 s 内没有任何层响铃），而停顿看门狗
  在整个读取期间保持开启。
- 一个正在等待的较短请求会在该读取的下一个分块处接管（`BYIELD`），即使没有槽位在解码时也是如此：该运行在
  那里结束，流水线被排空，已读取的部分等在一个槽位中，与非流水线时相同。没有人在等待的读取不会被切断。
- 在以下情形该功能是关闭的（只说明一次）：读取的线程会在那里分配或释放（`STRATA_PREFILL_HELP=1`、
  `STRATA_SPLIT_MTP_BATCH=1`）；服务门铃会发起一次 CUDA 调用（`--pcie-mode dma`、`STRATA_FS_SLOTS`，
  助手缓存 `--expert-cache-device1..3`）；以及使用会交出可回收缓冲区源的专家源（就地的 GGUF、一个不带缓冲的
  源、`STRATA_IO_PREFETCH`）：此时专家来自内存 arena 或映射的文件。带图片的提示词按常规方式读取。

每次读取一行日志（`strata batch: read N tokens on a thread of its own in X ms (concurrent, to Q of T); the slots
decoded R rows meanwhile (S rows/s; stage k: W windows, H ms host each)`）。已为 CUDA 与 HIP 构建（HIP 保持默认的
流优先级，且这里未在 GPU 上运行过）；SYCL 没有该功能。

## 与流水线组并行读取提示词（可选开启）
<a id="a-prompt-read-beside-pipelined-groups-opt-in"></a>

带层切分且 `--batch-groups` 大于 1 时，一个提示词会在一次运行中读完：每个正在 decode 的槽位都会停下直到它
读完，无论有多长，`STRATA_BATCH_DECODE_SHARE` 不适用，也不会接受任何 `BYIELD`（对流水线组
`batch_read_piece` 返回 0；#1906）。单块 GPU 没有这个问题：那里槽位会在提示词各分块之间解码
`STRATA_BATCH_DECODE_SHARE` x 该分块的耗时。下面这些变量把同样的选择交给流水线组：

- `STRATA_PIPED_READ_PIECE=N`：在流水线组上的一次提示词读取按每次 N 个 token 进行，向下取整到完整的分块
  （至少一个，最多 32 个），因此一段读取的分块与一次完整运行所取的完全相同，两级在其内部保持重叠，只有
  一段的结束才排空流水线。在两段之间，各槽位组通过流水线解码 `STRATA_BATCH_DECODE_SHARE` x 该段的耗时，
  最多 `STRATA_PIPED_DECODE_MAX_MS`，至少 `STRATA_PIPED_DECODE_MIN_MS`，并且在下一段之前，所有在途的组
  都会结束，如同任何提示词读取之前一样。
- 在一段的结束处流水线被排空，所以一个正在等待、提示词长度不足一半的请求可以在那里接管（`BYIELD`，
  与非流水线路径上各分块之间相同）：已读取的部分等在一个槽位中，短请求进入后读取从那里继续。即使没有槽位
  在解码，各段也是这样取的，原因就在于此（非流水线路径上，同一读取那时会分成
  `STRATA_BATCH_YIELD_CHUNKS` 段进行）。
- 一次读取若开始于上一次同类读取结束后一秒之内（加上解码预算）——提示词接连到达——会先给各槽位一次解码
  预算（同样的规则，从上一次读取最后一个完整分段起算）；否则各槽位会为两次读取都停下来。

这些变量未设置时，读取与之前一样是一次完整运行。每个分段一行日志（`strata batch: piped read N tokens in X
ms (to Q of T)`，有槽位解码时附上 `, then the slots decoded R rows in Y ms`），每次让路一行
（`the prompt read gives way at Q of T tokens; slot S holds it`），每次接续读取一行
（`a read right after a read: the slots decoded R rows in Y ms first`）。

**它拿什么来换。** 每个分段都以排空流水线收尾，所以一次长读取要花更长时间——在空闲的服务器上也是如此，
因为正是这些分段让短请求得以进入——而正在 decode 的流会在原本毫无进度的地方拿到 token。这是一个等待时间的
取舍，不是吞吐收益：在吞吐或长提示词自身的 TTFT 最重要时请保持关闭；当一条流停住好几秒、或一个短问题卡在一次
长读取之后，比长提示词多等一会儿更糟时，就使用它。

## 显存专家层在批量 window 中持续自适应
<a id="the-vram-expert-tier-keeps-adapting-in-batch-windows"></a>

批量 window 会统计它们路由到哪些专家层，并且每 `--adapt-every` 个 window（默认 4）引擎会把未放入显存的
专家中被路由最多的那些换入缓存，替换掉常驻中被路由最少的那些，与单独处理路径使用同一规则
（`--adapt-swaps` 与 `--adapt-decay` 同样适用；层切分时每块 GPU 的缓存都会自适应）。当该层不是整个模型、
且 `--adapt-every` 与 `--adapt-swaps` 都大于 0 时它会运行。默认情况下，那一轮与该 window 的提交和草稿并行，
并在下一个 window 开始之前完成。当在解码 window 之间读取一个长提示词时它保持静止（该提示词可能持有缓存槽位
的借用）。`strata batch:` 日志行会显示各轮与换入换出、每一级的 GPU 可达等待与池耗时，以及每个 window 由
显存层、PCIe 份额和 CPU 分别服务了多少个被路由的条目。换入换出会在 GPU 与 CPU 之间移动专家层，而两者舍入
方式不同，所以贪心输出可能逐次运行不同；`--adapt-every 1000000` 会固定该层（如同下文精确性设置那样）。
流水线的 `--batch-groups` 路径不自适应。

有了 `--adapt-async 1`（需要常驻内存模式），那一轮不会拖住一个 window：每个批量 window 把该轮推进一步
（表变更与上传在主线程，拷贝在一个助手线程与各卡的重填流上），与单独处理路径相同。一个到来的请求会在自己
开始之前完成在途的那一轮，而在解码 window 之间的一次提示词读取不会推进它。`--adapt-min-gain F`（默认 1.5）
会抬高一次换入换出必须越过的门槛（要进来的专家的路由计数对照要出去的那个），于是每轮移动的专家更少；两个层
都使用它。日志行中的 `adapt wait` 是主线程每 window 在该层上花掉的时间（阻塞式的层：等待它自己那一轮）。

使用与上文 `--batch-mtp` 数字相同的环境实测（2x RTX 3080 20 GB、UD-Q4_K_XL、`"layer_split": "23"`、
`"parallel": 2`、`--batch-mtp`、带我们生产栈的引擎 0.1.41；两个并发贪心 decode，各流 tok/s 相加，
每次重启 20 个测量值的中位数）：

| 层 | 合计 tok/s | 重启次数 | 每 window | 由显存服务的被路由条目 |
| --- | --- | --- | --- | --- |
| `--adapt-async 1 --adapt-every 2` | **89.2** | 3 | 34.6 ms，adapt wait 0.2 ms | 92.1% |
| 阻塞式，`--adapt-every 2` | 74.7 | 1 | 41.4 ms，adapt wait 8.4 ms | 92.3% |
| 无，缓存固定在层在相同提示词上学到的一份配置档上 | 69.5 | 1 | 43.6 ms | 77.2% |
| 无，`--adapt-every 0` | 45.2 | 2 | 66-68 ms | 52.7% |

该开关也会改变单独处理路径中的该层（没有只针对批量 window 的开关），所以这张表比较的是整个该层，
而不是"仅批量 window"：单独 decode 速度以同样的方式变化（81.7、66.3、69.0 与 43.1 tok/s）。这些提示词
是基准测试自带的，八个反复出现的主题，该层能很快学会，所以在更多样的工作负载上收益可能更小（未测量）。
上游主干在批量 window 中不运行任何该层，且这里没有针对上游二进制做过比较。

## 精确性
<a id="exactness"></a>

一个批量行的算术与单 token window 的相同，所以在贪心解码下**批量中的每个对话都产出它与单独运行时
完全相同的 token**——对 8 个各 150 个 token 的并发对话逐 token 验证过，带与不带流水线
（`tools/batch_test.py`）；并在一块 RTX 5070 上针对 4 个对话、在另两个对话解码时读取一个长提示词、
一个让了路并继续的提示词、从它的槽位续写的下一轮（从它持有的全部内容续写，以及从它不含回答思考部分的
轮次检查点续写），以及一个在其槽位中被停止并改由单独处理路径继续的请求验证过
（`tools/batch_interleave_test.py`）。以下设置能让比较是精确的：

- `STRATA_IQ_MT_MIN=1`（对每个组都使用多 token 的 CPU 专家内核，如同单独处理路径自己的精确性测试那样：
  默认情况下一个专家的单独行与在组中的行舍入方式不同，因此输出取决于一个 window 中有多少行共用某个专家
  ——而这一点在批量与单独请求之间是不同的），
- `--pcie-frac 0`：未命中专家中走 PCIe 的那部分是按每个 window 根据该 window 的未命中情况选定的，
  所以同一个专家可能在一个 window 里跑在 GPU 上、在另一个 window 里跑在 CPU 上，而两者舍入不同，以及
- `--adapt-every 1000000`（固定显存层），以及在解码槽位旁读取提示词时的 `--no-prefill-borrow`：
  那样它们的 window 看到的是不含被该提示词借走那些槽位的专家缓存（那些专家会跑在 CPU 上）。

在本 fork 的两块 V100 上实测（Q2_0、int8 KV、32,768 token 上下文、两个槽位、带上述设置的
`tools/batch_test.py`）：每个槽位生成的 128 个 token 与它单独运行的结果逐 token 相同。两次接纳花了
1.3 s，而两个 128 token 的回答（合计 256 个 token）在 5.8 s 内解码完毕，合计 44.0 tok/s
（从第一个 token 起算是 49.6 tok/s）。使用默认设置时输出仍然连贯，但在若干 token 之后会彼此偏离，
就像两个 window 组成不同的单独运行之间那样。在 RTX 5070 上实测（Q2_0、4 个各 200 token 的对话、
不带上述设置的 `tools/batch_test.py`）：一个与其单独运行的结果相同，其余从第 0、99 与 174 个 token
起出现差异——其中一个在第一个 token 就不同，因为自适应显存层在两次单独运行与批量之间移动过专家层；
四段文本的可读程度都与它们各自单独运行时相当。

带采样的请求（temperature、top_p、top_k、min_p、seed）是逐行抽取的，使用单独 window 的基于计数器的
抽取（Philox(seed, position)）。

## 限制（暂时）
<a id="limits-for-now"></a>

- 默认情况下，批量 window 不携带 MTP 草稿：槽位中的对话每个 window 解码一个 token（单独处理路径保留它的
  草稿，这就是为什么单独一个请求不会被放进槽位，以及当它被独自留下时会回到那里）。
- `--batch-mtp` 每个槽位使用一个提案。带层切分时它需要每个级各占一块 GPU，不与 `--batch-groups` 大于 1
  组合（流水线的槽位组不运行草稿，#1413），且未配合助手专家缓存运行过。
- 批量 window 中不应用 repetition / frequency / presence 惩罚。
- 短于一个分块的提示词会一次读完（各槽位会为它等待）；一次读取只在分块边界处让路，且不因图片让路。
- 接纳一次一个：两个新的长提示词会依次读取。
- `--batch-groups` 需要每个级各占一块 GPU。一个流水线槽位会再次成为一份对话缓存（0.1.41）：被独自留在
  其槽位中的请求会带着它的草稿回到单独处理路径，与单块 GPU 上相同。
- 各槽位的会话会占用显存（见上文）以及，在 KV 流式化时，页锁定内存。

## 实测
<a id="measured"></a>

一块 RTX 5070（12 GB）、Ryzen 5 7600、64 GB DDR5、Q2_0、32K 上下文，经由 HTTP 服务端：同时发送 C 个
不同请求（每个都是 800 词的作文，每个回答 256 个 token，贪心，关闭思考），3 轮的中位数：

| 并发数 | 设置 | 合计 tok/s | 相对一次一个 | 每请求 tok/s | 第一个 token：中位数 / 该轮最后 |
| ---: | --- | ---: | ---: | ---: | ---: |
| 1 | 一次一个（默认；setup 在这块卡上推荐的就是它） | 74.3 | - | 83.6 | 0.4 s / 0.4 s |
| 1 | `"parallel": 2` | 67.3 | -9 % | 74.8 | 0.4 s / 0.4 s |
| 1 | `"parallel": 4` | 57.9 | -22 % | 63.8 | 0.4 s / 0.4 s |
| 2 | 一次一个 | 71.6 | - | 77.3 | 2.1 s / 4.1 s |
| 2 | `"parallel": 2` | 61.0 | -15 % | 32.6 | 0.5 s / 0.9 s |
| 2 | `"parallel": 4` | 54.6 | -24 % | 28.7 | 0.6 s / 0.7 s |
| 4 | 一次一个 | 70.7 | - | 79.6 | 6.0 s / 11.2 s |
| 4 | `"parallel": 2` | 61.2 | -13 % | 32.2 | 4.5 s / 9.3 s |
| 4 | `"parallel": 4` | 63.1 | -11 % | 16.9 | 1.0 s / 1.8 s |

在这块卡上，槽位买到的是**等待时间，不是速度**：四个请求中的第四个在 1.8 s 后开始而不是 11.2 s，但它们
一起解码比一个接一个慢 11-24 %，而单独一个请求损失 11 %（2 个槽位）或 24 %（4 个槽位），因为各槽位的
会话（每个 0.56 GiB）要从专家缓存里出，而大多数专家跑在 CPU 上：一个跨 4 个对话的批量 window 每层读取
24 个 CPU 专家，而一个对话约 8 个，所以它的代价与那 4 个 token 逐个请求的代价大致相同（引擎日志中的
`strata batch:`：每个 4 行 window 54 ms，每个 1 行 window 约 20 ms）。这就是 setup 让 12 GB 卡保持
一次一个请求的原因。能把大多数专家留在显存中的卡，以及层切分，才是槽位同时也能增加速度的场景（见下文）。

一份历史的上游实测使用一个 4 GPU 层切分（4 x 16 GB，PCIe Gen3）、IQ3_S、八个槽位、四个流水线组，
并做了级权重裁剪。每个 HTTP 回答包含 400 个 token，temperature 0.7（PR #559）：

| 并发请求数 | 每请求 | 合计 |
| ---: | ---: | ---: |
| 1 | 123 tok/s（单独处理路径） | 120 tok/s |
| 2 | 57 tok/s | 113 tok/s |
| 4 | 51 tok/s | 205 tok/s |
| 8 | 45 tok/s | 360 tok/s |

在引擎 0.1.40.3 带下列补丁、并开启停放时，经由该服务：8 个请求在 temperature 0 下为 369 tok/s，
在 0.7 下为 358 tok/s。

单独一项级权重裁剪把那台机器上保存在显存中的专家份额从每块卡的 76-85 % 提高到 84-100 %。这是一次上游的
实测，不是 V100 的实测。

### 所有槽位共用一次启动（可选开启）
<a id="one-launch-for-all-slots-opt-in"></a>

在一个批量 window 中，QSA 块打分、top-k 与 decode 注意力是每行一次启动，而 GDN 递归（在 window 中以及
在 1 行的提交中）是每槽位一次启动。下面两个开关把它们各自改为对所有行一次启动，每一行仍然读取它自己那个
槽位的索引器 key、K/V 池与 GDN 状态（以内核参数的形式传值，所以按每行布局捕获的计算图仍然有效）：

| 开关 | 它做什么 |
| --- | --- |
| `STRATA_BATCH_ATTN_ROWS=1` | 该 window 所有行（最多 8 行）的块打分、top-k 与 decode 注意力各用一次启动完成。不与 KV 流式化同用（`kv_mode` 为 1 的槽位保留每行一次的启动）。 |
| `STRATA_BATCH_GDN_GROUPS=1` | 该 window 中的 GDN 递归，以及 1 行各组的提交，对所有槽位一次启动完成。各 conv 的提交仍按槽位。 |

两者默认关闭；关闭时引擎运行与以前完全相同的启动序列。开启时，每行的算术相同：4 个并发提示词在
temperature 0 下产出的字节与不开启时相同，`--batch 4` 与 `--batch 8` 都是如此。

## 与对话停放一同使用
<a id="together-with-conversation-parking"></a>

`--conversation-cache-mib N --conversation-cache-slots K`（DETAILS.md）与层切分一同工作也能用：一个其
对话被停放的请求，在其接纳之前会在每个级上被恢复，所以一个 agent 与它的各个子 agent，或几个轮流出现的
聊天，都能在不重新读取历史的情况下回来。在同一个 4 GPU 切分上实测，两段长对话通过 HTTP 服务端交替进行：
最初的几轮分别用 3.9 s 与 5.7 s 得到第一个 token（它们的提示词被读取），后续轮次是 0.53 s 与 0.46 s。

V100 fork 还保留了可选的磁盘层（`--conversation-cache-disk` 与 `--conversation-cache-disk-gib`）。
单独处理与批量接纳都能恢复一条匹配的磁盘记录。磁盘存储在接纳期间会保存即将换出的主会话；替换一个被持有的
批量槽位本身并不会把那个槽位保存到磁盘。不要假定每个被驱逐的槽位都有一条 L3 记录。一次接纳的系统提示词根
会被独立于槽位状态捕获进内存与磁盘两层：即使曾持有它的那个槽位被替换掉了，一个新聊天仍能复用它共享的
系统提示词。该根只会在对话记录之后才被驱逐（见 DETAILS.md 中的
`--conversation-cache-keep-root` 与 `--conversation-cache-disk-keep-root`）。

## 测试
<a id="testing"></a>

有四个脚本驱动一个已构建的引擎或一个运行中的服务端；每个都在失败时以非零退出。`serve/test_parallel.py`
用一个脚本化的引擎（不需要 GPU）测试服务端那一侧。

| 脚本 | 它检查什么 |
| --- | --- |
| `tools/batch_test.py` | 同样的提示词单独运行（`GEN`）与一起放进批量槽位（`BGEN`）：每个槽位的贪心 token 等于它单独运行时的 token；打印合计速率。`--extra` 里给 `--batch-groups` 可测试流水线，`--keys "temperature=0.7"` 可测试带采样的行。 |
| `tools/batch_interleave_test.py` | 在两个槽位解码时读取一个长提示词、一个让路（`BYIELD`）并继续的提示词，以及从它的槽位续写的下一轮：每一段都等于它单独运行时的 token。在带流水线组的两级层切分上，请在 `--extra` 中加上 `--batch 4 --batch-groups 2`（它的 3 个槽位不能分成两组）并设置 `STRATA_PIPED_READ_PIECE`；请在不带对话缓存的情况下运行它，否则第 4 步会恢复提示词而不是读取它。 |
| `tools/parking_test.py` | 对一个对话的后续轮次，无论它的状态是保持活跃还是从停放缓存回来，都解码相同的 token（带层切分时：每一级的镜像）。 |
| `tools/early_close_test.py` | 一个提前停止读取流式回答的客户端（单独，以及第二个请求正在运行时）不会把它的 token 留给下一个请求（服务端）。 |

要做精确比较，请传入 `--pcie-frac 0 --adapt-every 1000000`（并且这些脚本会设置 `STRATA_IQ_MT_MIN=1`）：

```
python3 tools/batch_test.py --exe engine/strata --config strata-<model>.json --batch 8 --n 8 \
    --extra "--layer-split 12,24,36 --batch-groups 4 --pcie-frac 0 --adapt-every 1000000"
python3 tools/batch_interleave_test.py --exe engine/strata --config strata-<model>.json \
    --extra "--pcie-frac 0 --adapt-every 1000000 --no-prefill-borrow"
python3 tools/parking_test.py --exe engine/strata --config strata-<model>.json \
    --extra "--layer-split 12,24,36 --conversation-cache-mib 8192 --conversation-cache-slots 4 --pcie-frac 0"
STRATA_KEY=<key> python3 tools/early_close_test.py http://127.0.0.1:8080
```

对于单 GPU 的 `--batch-mtp`，请使用一个带有 `rt/draft_vocab.bin` 的模型，以便用共享的草稿词表头来测试
接纳。这会拿两个槽位的输出与单独解码作比较：

```
python3 tools/batch_test.py --exe engine/strata --config strata-<model>.json --batch 2 --n 2 --max-new 64 \
    --extra "--batch-mtp --pcie-frac 0 --adapt-every 1000000"
```

## 引擎协议（`--serve`）
<a id="engine-protocol---serve"></a>

在 `GEN` / `GENI` 之上：

| 指令行 | 方向 | 含义 |
| --- | --- | --- |
| `BGEN <slot> <max_new> [keys] <ids>` | 入 | 读取提示词（如同 `GEN 1`），然后在 `<slot>` 中继续 |
| `BGENI <slot> <max_new> [keys] <file> <ids>` | 入 | 同样的操作，带图片 |
| `BADM <slot> <1/0>` | 出 | 在接纳的 `DONE` 之后：1 = 它在该槽位中继续，0 = 它已结束 |
| `BT <slot> <id>` | 出 | 该槽位的一个 token |
| `BDONE <slot> <generated> <stop/length/cancel> <ms>` | 出 | 该槽位重新变为空闲（它保留它的对话） |
| `BSTOP <slot>` | 入 | 在该槽位下一个 window 处结束它 |
| `BYIELD <slot>` | 入 | 正在读取的提示词会在其下一个分块边界处让路；已读取的部分等在一个 `<slot>` 中（接纳自己的那个槽位，或单独请求的一个空闲槽位） |
| `YIELDED <slot> <tokens>` | 出 | 在一次让了路的读取的 `DONE cancel` 之前：该请求稍后会被重新发送，并从那里继续 |
| `INFO ... batch_slots=N` | 出 | 引擎实际运行的槽位数（仅在带 `--batch` 时） |

`tools/batch_test.py` 直接驱动引擎：同样的提示词先单独、再一起运行，逐 token 比较，并给出合计速率。
